### План реализации Swagger‑подобного Testy Viewer с валидацией по схеме

#### 1) Требования и MVP
- Отображать .testy.yml строго по JSON Schema (верхний уровень — массив сценариев).
- Панель‑вьювер рядом с редактором: список сценариев и их шагов, как в Swagger.
- Цветовая индикация HTTP методов и статусов, краткие сводки по fixtures/mocks.
- Валидация документа по встроенной схеме `testy.json`; отображение ошибок/предупреждений в UI с навигацией к месту в YAML.

#### 2) Схема и ресурсы
- Перенести `testy.json` под `src/main/resources` и грузить через `classLoader`.
- Обеспечить версионирование схемы (поле `title/version`), подготовить API загрузки.

#### 3) Парсер YAML → модель (по схеме)
- Реализовать парсинг верхнего уровня: `Sequence` из объектов сценариев.
- Извлекать:
  - Scenario: `name`, опц. `fixtures`, `mockServers`, `mockCalls`, `steps`, `offset`.
  - Step: `name`, `request.{method,path}`, `response.status`, `offset`.
- Сопоставлять элементы PSI к оффсетам для навигации.
- Толерантность к неполным данным: сценарии/шаги с пропусками отмечать как «неполные» (warning) даже до валидации схемой.

#### 4) Валидация по JSON Schema
- Зависимости: SnakeYAML для загрузки YAML → Map/List; JSON Schema Validator (предпочтительно `com.networknt:json-schema-validator`) + Jackson.
- Загрузка схемы из ресурсов, компиляция валидатора на старте панели (кэшировать).
- Валидация всего документа; сбор ошибок (JSON Pointer → сообщение/код).
- Маппинг JSON Pointer → PSI offsets (best effort): сначало по точному пути, иначе ближайший родитель; формирование `Problem(severity, pointer, message, offset)`.

#### 5) UI панели (Swagger‑подобный Tree)
- Структура дерева:
  - Root: имя файла + сводка (кол-во сценариев/ошибок).
  - Scenario node: `name` (+ краткое `description` если будет); индикатор валидности/кол-ва ошибок.
  - Children:
    - Steps: показывать `METHOD` (цветной бейдж) + `path` + `→ status`.
    - Fixtures/Mocks: сводные узлы (например, «fixtures: 3», «mocks: 2 servers, 7 routes»).
    - Errors: группа «Problems (N)» с подузлами сообщений, если уместно.
- Цвета HTTP методов: GET — синий, POST — зелёный, PUT — оливковый, PATCH — фиолетовый, DELETE — красный, прочие — серые.
- Цвета статусов: 2xx — зелёный; 4xx/5xx — оранжевый/красный; unknown — серый.
- Tooltips по наведению: полный текст ошибки/сводной информации.
- Значки/иконки: простые (встроенные AllIcons) либо минимальные SVG при необходимости.

#### 6) Навигация и интерактивность
- Двойной клик/Enter по узлу сценария/шага/ошибки → `OpenFileDescriptor(project, file, offset).navigate(true)`.
- Контекстное меню: «Reveal in Editor», «Copy JSON Pointer», «Expand/Collapse».
- Панель команд сверху: «Refresh», «Expand all», «Collapse all».

#### 7) Живое обновление
- Подписка на изменения документа/PSI `PsiTreeChangeListener` или `EditorFactory` + `DocumentListener` для конкретного файла.
- Дебаунс репарсинга/валидации (например, 250–400 мс).
- Сохранение состояния разворота и выбранного узла при перерисовке.

#### 8) Интеграция/Градация ошибок
- Классификация: error (schema violation), warning (неполные/подозрительные узлы), info (подсказки).
- Агрегация по сценарию: на узле сценария суммарно показывать число проблем.

#### 9) Градл и совместимость
- Добавить зависимости в `build.gradle.kts` (implementation): SnakeYAML, Jackson, networknt json-schema-validator совместимых версий (Java 17+, IJ 2025.2).
- Отсечь их из тестового рантайма при необходимости (минимизация размера плагина не критична на MVP).

#### 10) Тестирование
- Unit (без IDE):
  - YAML→Map конвертация: валидные и невалидные примеры.
  - Валидация схемой: набор позитивных/негативных кейсов (минимум 4–6).
- LightPlatform (интеграционные, позже):
  - Парсинг PSI на оффсеты сценариев/шагов.
  - Навигация из панели в редактор.

#### 11) Performance/UX
- Кэширование последнего результата парсинга/валидации для быстрого отображения.
- Safety‑rails: защита от очень больших файлов (обрезать количество отображаемых проблем, предупреждение).

#### 12) Документация
- README: описание возможностей.viewer, поддерживаемый формат, как включить/использовать, известные ограничения.
- Скриншот панели.

#### 13) Этапы и критерии готовности
- Этап 1: Парсер + базовое дерево сценариев/шагов (без валидации). Критерий: видны сценарии/шаги, навигация работает.
- Этап 2: Валидация по схеме и отображение ошибок в дереве. Критерий: ошибки подсвечиваются и ведут к месту.
- Этап 3: Цвета/бейджи/сводки (fixtures/mocks), тултипы. Критерий: удобный обзор «как у Swagger».
- Этап 4: Живое обновление и UX‑полировка. Критерий: автоперестроение без лагов, сохранение состояния дерева.
